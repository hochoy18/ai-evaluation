Agent 评测全流程
从 @observe 插桩 到 CI 门禁

以「订明天纽约→洛杉矶最便宜航班」为例，把整条链路讲透：运行期边跑 agent 边录 trace（应用 LLM 干活，0 次裁判）；评测期读这棵 trace 树调 judge 打分。@observe / update_current_span / update_current_trace 全在运行期，作用是把评测要用的数据和指标，预先挂到 trace 树的正确位置。

应用 LLMapp_client · 真正决策/生成
插桩三件套记录轨迹 + 挂数据/指标 · 不调 LLM
裁判 LLMjudge_model · 评测期打分
1

全景：两个阶段，三类角色

先建立总图——评测不是「跑 agent 时顺便打分」，而是「先录后评」两段式。
核心一句话 插桩三件套全在「运行期」，它们不调用任何 LLM，只负责把「评测要用的数据 + 指标对象」挂到 trace 树的正确节点上。真正调 judge 的，是评测期的 metric.measure()。
2

运行期：逐步走一遍 agent

基线任务「订明天从纽约到洛杉矶最便宜的航班」。看每个插桩函数作用在哪个环节。
1

进入 travel_agent @observe(type="agent")

创建 agent span（整棵树的根），开始计时，自动捕获入参 user_input。

▷ 对评测：没有根，StepEfficiency 无从审计整棵树，TaskCompletion 没有 trace 可读。

2

构造 system prompt（业务逻辑）

注入「今天 2026-11-19，明天即 2026-11-20」，让 LLM 能解析「明天」。（漏了这步，TaskCompletion 曾跌到 0.05）

3

第一次决策 call_llm @observe(type="llm")应用 LLM ①

建 llm span①，自动记 input=messages / output / token。应用 LLM 决定「先 search_flights」。

因 msg.tool_calls 存在 → update_current_span 给这个决策 span 挂 tools_called / expected_tools / metrics=[ToolCorrectness, ArgumentCorrectness]。

▷ 对评测：组件级指标必须挂在「做工具决策的 llm span」上，且有数据可评。

4

执行 search_flights @observe(type="tool")

建 tool span，自动记入参与返回 [{FL123,$450},{FL456,$380}]。

▷ 注意：工具在 travel_agent 循环里执行，所以 tool span 是 agent 的子节点（与 call_llm 平级），不是 llm 的子节点。

5

第二次决策 call_llm @observe(type="llm")应用 LLM ②

建 llm span②；搜过了 → 决定 book_flight。update_current_span 再挂组件指标（expected=book_flight）。

6

执行 book_flight @observe(type="tool")

建 tool span，返回 {confirmation:"CONF-789", flight_id:"FL456"}。

7

最终回复 call_llm @observe(type="llm")应用 LLM ③

建 llm span③，生成「已预订 FL456 · $380 · CONF-789」。tool_calls 为空 → 不挂组件指标（无工具决策可评）。

8

收尾 update_current_trace

给 trace 根挂整体 input / output / 全程 tools_called 汇总 / expected_tools=[search, book]。

▷ 对评测：TaskCompletion 要从 trace.input 推断 task、从 output 提取 outcome——没这步就没有「任务/结果」可对比。

9

travel_agent 返回

agent span 关闭，整棵 trace 树录好。运行期结束：3 次应用 LLM 调用，0 次裁判调用。

3

录好的 Span 树（评测对象）

结构经真实 test_run_*.json 核实：tool 与 call_llm 平级挂在 agent 下；每个 call_llm 内嵌一个 SDK 自动插桩的 chat span。
易错点（已核实纠正） tool span 的父节点是 agent，不是 llm——因为工具是在 travel_agent 循环里、call_llm 返回之后才执行的，此时 llm span 已关闭。每个 call_llm 内部那个 chat span，才是 SDK 自动插桩的真正模型调用。
4

三件套各自的作用环节

一句话：@observe 搭骨架，update_current_span 挂局部语义，update_current_trace 挂全局语义。
函数作用环节记录什么对评测的作用
@observe(type=...) 每个函数进入/退出时 自动建 span 节点 + 入参/返回/耗时/嵌套 搭骨架：没有 span 树，轨迹级指标无对象可评
update_current_span 做工具决策的 llm call 内 该次决策的 tools_called / expected_tools / 组件指标对象 挂组件级：让 ToolCorrectness / ArgumentCorrectness 有数据、有归属
update_current_trace agent 收尾时 整体 input/output / 全程工具汇总 / expected_tools 挂轨迹级：让 TaskCompletion 有 task/outcome，StepEfficiency 有完整树

它们记录的数据长什么样（ToolCall）

tools_called / expected_tools 都是 List[ToolCall]，序列化后字段转驼峰：

// 你真实 test_run_*.json 里的 toolsCalled（agent 根，全程汇总）
[
  { "name": "search_flights", "type": "FUNCTION",
    "inputParameters": {"origin":"纽约","destination":"洛杉矶","date":"2026-11-20"},
    "output": [{"id":"FL123","price":450},{"id":"FL456","price":380}] },
  { "name": "book_flight", "type": "FUNCTION",
    "inputParameters": {"flight_id":"FL456"},
    "output": {"confirmation":"CONF-789","flight_id":"FL456"} }
]
记录 ≠ 评测：metrics 存的是「对象」不是「分数」 记录时 span.metrics = [ToolCorrectnessMetric实例, ...]，只有 threshold/model 等配置，没有 score。要等评测期 measure() 调 judge 后，才生成 metricsData（name / score / threshold / success / reason）。
5

评测期：assert_test 内部做了什么

它是「执行 + 断言」的外层编排：组装用例 → DFS 调 measure → 汇总 → 不达标就 raise。

它干的三件事

① 组装用例：golden（输入/期望）+ 活 trace（实际执行）拼成 LLMTestCase。

② 触发评测：DFS 遍历 span，调 metric.measure() → 调 judge。

③ 翻译成败：分数达标与否 → pytest 通过 / AssertionError 失败。

它不做什么

不重新跑 agent——agent 前面已跑完，trace 已录好，它只是「读」出来。

不在记录时打分——update_* 挂的指标对象，到这一步才真正 measure。

6

judge 到底何时被调用

关键：不在跑 agent 时，而在「循环体结束、控制权交回迭代器 / assert_test」之后。逐条交替：跑一个 → 评一个。
调用发生位置调 judge？
update_current_span / traceagent / llm call 内部❌ 0 次，纯记录
metric.measure()assert_test 的 DFS / evals_iterator 评测阶段✅ 这里才调

批量总量：N 个 goldens × 约 4 次轨迹级裁判调用（TaskCompletion / StepEfficiency 各约 2 次）+ 组件级裁判调用 + N 次 agent 运行。数据集大时易触发百炼限流——这是评测「卡住」的常见原因。

7

数据 → 指标：插桩对评测的具体作用

每个指标「吃」的，正是运行期挂上去的那部分数据。数据挂错位置或缺失，对应指标就评不了。
指标层级挂在哪吃哪些 recorded 数据评什么
ToolCorrectness 组件级 llm 决策 span①② span.tools_called vs span.expected_tools 这次决策选对工具没
ArgumentCorrectness 组件级 llm 决策 span①② tools_called.input_parameters（+input） 工具参数对不对（城市/日期）
TaskCompletion 轨迹级 trace 根 trace.input→task，trace.output→outcome 整件事做成没（订到最便宜航班）
StepEfficiency 轨迹级 trace 根 整棵 span 树的每一步 过程省不省（有无多余步骤）

评测后生成的 metricsData（基线实测）

// trace 根 metricsData（真实 test_run_20261119_163757.json）
[
  { "name":"Task Completion",  "score":0.98, "threshold":0.7, "success":true },
  { "name":"Step Efficiency",  "score":1.0,  "threshold":0.7, "success":true }
]

基线「正常 search→book」两步精简、目标达成 → 轨迹级双双高分。两种失败注入的对照很说明问题：

--fail-search · 被迫重试 首次搜索抛 504，agent 重试。judge 认为「错误恢复」合理 → StepEfficiency 不降（0.75→0.75）。必要的重试不是浪费。
--wasteful · 主动冗余 无错误也重复搜索「核对」。StepEfficiency 下降，且冗余决策 span 的 ToolCorrectness 同步下降——「答案对、过程烂」：轨迹分报警，组件分定位病灶。
8

断言 → CI 门禁

把「分数达标与否」翻译成「pytest 通过/失败」，就是门禁的落地机制。
if test_result.success is False:
    # 收集所有失败指标，拼成详情
    raise AssertionError(
        f"Metrics: TaskCompletion (score:0.4, threshold:0.7, ... reason:...) failed.")
# success=True → 静默返回 → pytest PASSED

不达标 → raise → pytest FAILED → 进程非零退出 → CI 红灯 → 挡住合并。达标 → PASSED → 绿灯放行。

PyCharm 点绿色三角默认会失败 assert_test(golden=...) 需要「活 trace」，靠 deepeval pytest 插件的 eval scope，而插件被环境变量 DEEPEVAL 开关控制。deepeval test run 会自动设 DEEPEVAL=true；PyCharm 裸 pytest 没设 → 报 No active trace found。
解决：在 Run Configuration 的 Environment variables 加 DEEPEVAL=true（并用项目 .venv 解释器），即可点绿色三角运行。
运行方式DEEPEVAL插件 eval scope结果
uv run deepeval test run ...自动 true激活✅
PyCharm 绿色三角（默认）未设跳过❌ No active trace
PyCharm + DEEPEVAL=truetrue激活✅
运行期只管「如实记录 + 把指标挂到对的节点」，
评测期才「读树打分」——两者解耦。

@observe 负责结构（有哪些步骤、怎么嵌套）；update_current_span 负责局部语义（这一步决策对不对 → 组件级）；update_current_trace 负责全局语义（整件事成没成、省不省 → 轨迹级）。

三者配合，裁判既能「指着某个决策 span 说病灶」（组件分），又能「对着整棵树说整体病情」（轨迹分）。
